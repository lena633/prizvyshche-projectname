# Звіт про шар сховища (Storage)

## 1. Схема бази даних
Сховище реалізовано на базі **SQLite** та **SQLAlchemy 2.0** (`src/jobradar/storage/models.py`).
При кожному підключенні до бази даних через обробник події `connect` у `make_engine()` примусово вмикається перевірка зовнішніх ключів (`PRAGMA foreign_keys=ON`).

### Таблиця `budgets`

| Стовпець | Тип SQL | Обмеження / Індекси | Опис |
| :--- | :--- | :--- | :--- |
| `code` | `VARCHAR(255)` | `PRIMARY KEY` | Код бюджетної класифікації / громади |
| `name` | `VARCHAR(255)` | `PRIMARY KEY` | Назва статті видатків / бюджетного запису |
| `amount` | `INTEGER` | `NOT NULL` | Сума транзакції (у цілих одиницях) |
| `type` | `VARCHAR(255)` | `NOT NULL`, `INDEX (ix_budgets_type)` | Тип бюджетної операції |

**Ідемпотентність:** складений первинний ключ `(code, name)` у поєднанні з діалектним виразом `INSERT ... ON CONFLICT (code, name) DO NOTHING` гарантує, що повторний запуск конвеєра на тих самих даних (`jobradar data/large.jsonl --db data/jobradar.db`) записує `0` нових рядків і не створює дублікатів.

## 2. Міграції (Alembic)
Керування схемою налаштовано через **Alembic** (`alembic.ini`, `migrations/env.py`) із увімкненим режимом `render_as_batch=True` для коректної підтримки змін таблиць та індексів у SQLite.

Ланцюжок ревізій у `migrations/versions/`:
1. **`initial schema`** — створення базової таблиці `budgets` зі складеним первинним ключем `(code, name)`.
2. **`index on type`** — додавання індексу `ix_budgets_type` за стовпцем `type`.

Перевірено повний цикл накату (`alembic upgrade head`), відкату на одну ревізію назад (`alembic downgrade -1`), повернення на `head` та узгодженості схеми з ORM-моделями (`alembic check` → `No new upgrade operations detected.`).

## 3. Дослід 1: Вплив індексу та вибірковості стовпця
Вимірювання проведено на базі обсягом **154 114 записів** (`data/jobradar.db`) для двох стовпців різної вибірковості:
* **Висока вибірковість (`name`):** багато різних значень (пошук конкретного запису).
* **Низька вибірковість (`type`):** кілька повторюваних значень (фільтрація за типом, де збігається значна частка таблиці).

| Стовпець (вибірковість) | Стан | План виконання (`EXPLAIN QUERY PLAN`) | Середній час запиту | Прискорення |
| :--- | :--- | :--- | :--- | :--- |
| `name` (висока) | Без індексу | `SCAN budgets` | **44.403 мс** | — |
| `name` (висока) | З індексом `ix_budgets_name` | `SEARCH budgets USING INDEX ix_budgets_name (name=?)` | **0.121 мс** | **у 367.0 разів** |
| `type` (низька) | Без індексу | `SCAN budgets` | **242.598 мс** | — |
| `type` (низька) | З індексом `ix_budgets_type` | `SEARCH budgets USING INDEX ix_budgets_type (type=?)` | **156.531 мс** | **у 1.55 раза** |

**Висновок:** індекс змінює план виконання запиту з повного послідовного сканування всієї таблиці (`SCAN budgets`) на швидкий пошук за B-деревом (`SEARCH budgets USING INDEX`). Найбільший виграш (у **367 разів**) індекс дає на стовпці `name` із **високою вибірковістю**, оскільки одразу знаходить поодинокі рядки. На стовпці `type` із **низькою вибірковістю** виграш становить лише **1.55 раза**, тому що критерію відповідає велика частка записів таблиці, і SQLite все одно витрачає основний час на вичитування самих рядків із диска.

## 4. Дослід 2: Вплив межі транзакції (20 000 рядків)
Порівняння швидкості запису **20 000 рядків** у SQLite за двох стратегій керування транзакціями:

| Режим фіксації (`commit`) | Час виконання | Відносна швидкість |
| :--- | :--- | :--- |
| Коміт після кожного рядка (20 000 транзакцій) | **173.303 с** | 1× (базова) |
| Один коміт наприкінці (1 транзакція) | **0.044 с** | **у 3935.5 разів швидше** |

**Висновок:** кожен виклик `commit()` у SQLite ініціює окрему транзакцію та фізичну синхронізацію журналу на диск (`fsync`), що займає в середньому ~8.6 мс на один рядок. Коли всі 20 000 вставок об'єднано в одну транзакцію, синхронізація відбувається лише один раз наприкінці. Саме тому межа транзакції (`session_scope`) винесена на рівень точки входу (`CLI`), а репозиторій `SqlBudgetRepository.add_many()` виконує пакетну вставку (`batch_size=500`) усередині спільної сесії без проміжних комітів.
